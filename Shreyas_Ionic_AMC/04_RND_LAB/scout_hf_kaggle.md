## 1. Finance NLP (tone, NER, summarization)

**FinBERT (ProsusAI/finbert)** — already planned/adopted. 110M params (BERT-base), trivial CPU inference (<50ms/doc). 97% acc on Financial PhraseBank. Remains the safe default for EN financial-news tone. Baseline, not new.

**Fin-E5** (finance-tuned e5-mistral embedding model, from FinMTEB paper) — 7B param embedding model, beats general e5-mistral by +4.5% on FinMTEB (finance text embedding benchmark), esp. classification (0.842). CPU-inference NOT viable at 7B (too slow for a research desk without GPU on demand) — would need Kaggle T4 escape hatch for batch embedding jobs, or find a distilled/smaller variant. WATCH — reassess if a small Fin-E5 distillation appears.

**FinTwitBERT / FinTwitBERT-sentiment** (StephanAkkerman, HF) — BERT-base size (~110M), pretrained on 10M financial tweets, finetuned on 38k human-labeled + 1.4M synthetic tweet sentiment. CPU-viable (same class as FinBERT). Use case: social/Twitter-style short-form financial chatter tone — we don't currently ingest fintwit, so this unlocks a NEW input type (if we ever pull StockTwits/X data) rather than replacing FinBERT for news/filings. SKIP for now (no data source feeding it) but cheap to revisit if we add social data — WATCH.

**TinyBERT distilled from FinBERT via GPT-augmented distillation** (arXiv 2409.18999) — smaller/faster distillation recipe, not an off-the-shelf checkpoint we can just pull. Interesting technique if FinBERT inference ever becomes a bottleneck (it won't at our volumes). SKIP — no bottleneck to solve.

**Kronos** (shiyu-coder/Kronos, AAAI 2026) — NOT an NLP model; a decoder-only foundation model for OHLCV "K-line" sequences (tokenizes candlesticks, autoregressive transformer). Claims +93% RankIC over leading TSFM and +9% lower MAE on realized-vol forecasting vs 25 baselines on its own benchmark (self-reported, single-paper, not yet independently replicated). Open-source on GitHub. Directly relevant to our realized-vol / IV-RV sleeve. CPU-feasibility: smallest variant likely runs CPU for inference (needs verification of exact param count — repo has multiple sizes mini/small/base). NOW-to-WATCH boundary: worth a cheap-test (Gate-3) on our own NIFTY500 OHLCV before trusting self-reported numbers — self-reported single-paper benchmarks have a bad replication track record in this exact niche (see TSFM section below).

**Indian financial text models (HF):**
- `Vansh180/FinBERT-India-v1` and `kdave/FineTuned_Finbert` — FinBERT fine-tuned on India-focused financial news/headlines. Small (110M), CPU-viable. Community models (low download counts, unverified quality/provenance) — worth a quick eval (Gate-3 style: label 100 headlines by hand, compare to base FinBERT) before trusting over plain FinBERT. WATCH.
- `bharatgenai/BhashaBench-Finance` — Hindi+English financial knowledge BENCHMARK (19,433 Qs), not a model. Useful only if we ever eval a Hindi-capable model; we don't process Hindi text today. SKIP.
- L3Cube HindBERT/DevBERT — Hindi NER models, competitive with multilingual BERT on NER. Only relevant if source docs are Devanagari-script (they aren't — NSE/BSE filings, screener.in, trendlyne are English). SKIP.
- No credible NER model specifically for Indian tickers/company aliases found (e.g. resolving "RIL" / "Reliance" / "Reliance Industries Ltd" to one entity) — this looks like a gap we'd have to solve with a simple alias-dictionary + fuzzy match rather than a pretrained NER model. Cheaper and more reliable than any HF model found. NOTE not ADOPT.

**Filing/earnings-call summarization:** No standout open pretrained summarizer specific to Indian filings surfaced. `sweatSmile/phi3-mini-finance-nlp` (Phi-3-mini-4k, ~3.8B, fine-tuned on Indian annual-report Q&A) is CPU-marginal (3.8B is slow but not impossible on CPU for occasional/batch use, several seconds/query). Low download count / unverified — WATCH, needs a hands-on quality check before any adoption; general-purpose small LLMs (Phi-3-mini, Qwen2.5-3B-Instruct base, not finance-tuned) with a good prompt likely match or beat a low-provenance finance fine-tune for summarization — SKIP the specialized model, WATCH generic small-LLM-for-summarization as a pattern.

## 2. Time-series foundation models (Chronos, TimesFM, Moirai, Lag-Llama)

**Verdict: WATCH, not ADOPT — for exactly the reasons D-011 assumes.** Multiple 2025-2026 papers converge on the same finding:
- A late-2025 evaluation (arXiv 2511.18578, "Re(Visiting) TSFMs in Finance") comparing TimeGPT/TimeGPT-LH/TimesFM-2.5/Moirai-2.0/Chronos-1/Chronos-2 against from-scratch baselines (NBEATS, NHITS, PatchTST, iTransformer, KAN) on AAPL/JPM/GOOG/AMZN: pretrained TSFMs won 8/10 task-level rankings (Moirai-2.0 and TimesFM-2.5 strongest), BUT gains over a plain random-walk benchmark were "small and sparse" — a Diebold-Mariano test only rejected equal-or-worse-than-random-walk for Chronos on AMZN and Moirai-2.0 on GOOG. I.e., they mostly don't beat a random walk with statistical significance on single-name daily equity prices.
- Framed generously: TSFMs are "useful practical priors that reduce model-development costs in low-data settings, but not universal solutions for beating baselines on stock price prediction" (their own words).
- **Kronos** (see above) is the one model claiming a large, specific edge (+93% RankIC) but on its own author-selected benchmark suite vs 25 baselines — classic single-paper-strong-claim pattern we've been burned by internally (Red Team trophy wall). Needs independent replication or our own cheap-test before any weight is placed on it.
- Practical takeaway for us: we do NOT have a use case where raw next-bar/next-day price forecasting is the bottleneck — our edges are vol-risk-premium and event-driven, not point-forecast alpha. TSFMs would only be interesting for (a) realized-vol forecasting inputs to IV/RV sleeve, or (b) synthetic OHLCV data augmentation for backtesting thin-history stocks. Both are WATCH-tier "someday cheap-test" items, not current builds.
- Action if revisited: Chronos (Amazon, MIT-licensed, github.com/amazon-science/chronos-forecasting) is the easiest to actually run — has small checkpoints (chronos-t5-mini/small, tens of millions of params) that are CPU-viable for a quick cheap-test, unlike TimesFM/Moirai-2.0 which lean larger/GPU-oriented. If we ever cheap-test this family, start with Chronos-mini on CPU against our IV/RV realized-vol baseline.

## 3. Kaggle methods transferable to Indian markets

**Indian-market Kaggle work directly: thin.** Searched specifically — only static datasets exist (adritpal08/indian-stock-market-dataset, NSE bhavcopy mirrors, andrewmvd/india-stock-market, sameerprogrammer NSE/BSE financials for 4456 cos). NO active/high-quality Indian-market competitions or methods-rich notebooks found — these are upload-and-forget datasets with basic EDA notebooks, not a mined-methods opportunity. We already have better raw NSE bhavcopy access than these Kaggle mirrors (per KNOWLEDGE_BASE lesson #7, 210-name F&O universe). SKIP mining Indian-Kaggle specifically — nothing there we don't already have.

**Transferable METHODS from the three flagship competitions (the actual ask):**

- **Optiver Realized Volatility Prediction (2021):** Feature engineering patterns worth stealing wholesale: order-book-derived features (bid-ask spread, weighted avg price, order imbalance) via rolling-window aggregation over sub-windows of the prediction horizon (not just one aggregate stat per window — multiple sub-window slices catch within-window vol clustering). LightGBM was the dominant model class among top solutions, consistent with our own tooling (D-011). Directly applicable to our IV/RV sleeve: compute realized-vol features over multiple intraday sub-windows rather than a single daily RV, feed as LightGBM features. NOW — this is a free feature-engineering upgrade to an existing validated sleeve, no new infra needed.
- **JPX Tokyo Stock Exchange Prediction (2022):** The competition's EVALUATION METRIC is the more valuable export than any specific model: rank ~2000 stocks by predicted forward return, score = spread between top-200 and bottom-200 basket returns (a long-short spread portfolio, not raw regression R²/RMSE). This is a much better fitness function for cross-sectional equity ranking than pointwise return prediction — it directly measures what a long-short (or long-only top-decile) strategy would earn. Directly relevant to Track-2 momentum machine (cross-sectional stock ranking). NOW — adopt the evaluation framing (top-K minus bottom-K spread, computed out-of-sample per rebalance period) as the standard metric for any cross-sectional ranking model, replacing/supplementing plain IC.
- **Jane Street Market Prediction:** Main transferable idea is `weight`-aware evaluation (trades weighted by a utility/size weight, not just accuracy) and heavy emphasis on avoiding leakage from anonymized/proxy features via strict purged time-based CV — reinforces rather than adds to what mlfinlab/CPCV already gives us (see below). No Jane-Street-specific technique beyond that surfaced as novel for us.
- **Learning-to-rank losses (LambdaRank/LambdaMART):** LightGBM has a built-in `LGBMRanker` with `objective='lambdarank'` — directly usable with our existing LightGBM stack (zero new dependency). Optimizes NDCG-style rank metrics instead of MSE on raw returns, which fits a "pick the best N stocks this month" cross-sectional task better than a regression head. A very recent paper (arXiv 2605.00501, "LambdaRankIC") implements a custom lambdarank-style objective that directly optimizes Rank-IC / ICIR in XGBoost and reports best out-of-sample Rank-IC/ICIR vs return-prediction baselines — same trick portable to LightGBM's custom objective API. NOW — cheap to bolt onto the existing Track-2 momentum/cross-sectional pipeline; swap current regression objective for `lambdarank` or a custom Rank-IC objective and A/B against current approach.
- **Combinatorial Purged Cross-Validation (CPCV)** — not from a Kaggle competition per se, but the standard anti-overfitting CV method for exactly the kind of financial ML we do, implemented in `mlfinlab` (already in our reference library per KNOWLEDGE_BASE §B) and in various open GitHub notebooks/blog code (quantinsti, quantbeckman "with code" post). We reference mlfinlab already but should confirm CPCV specifically (not just plain purged K-fold) is actually wired into the Gate-4 backtest validation battery — it produces a full distribution of out-of-sample paths rather than one score, which is a strictly stronger overfitting check than a single walk-forward split. NOW — verify/upgrade Gate-4 to use mlfinlab's CPCV generator if not already doing so; this is process, not new capability, but closes a known gap between "reference library" and "actually used."

## 4. Embedding/RAG for KNOWLEDGE_BASE / memo search

Our KNOWLEDGE_BASE.md / IDEA_PIPELINE / memo corpus is small (markdown files, low thousands of docs at most) — this only needs a lightweight, CPU-only embedding model, not a frontier one.

- **all-MiniLM-L6-v2** (sentence-transformers) — 22-23M params, ~46-90MB on disk, single-digit-millisecond CPU inference per doc. Runs on virtually any machine, zero GPU need. Slightly lower retrieval accuracy than larger models but for a firm-internal memo/knowledge-base search (not a public-facing RAG product), this is very likely good enough. **NOW** — best fit for "search our own markdown files fast, no infra." Simplest to wire: `sentence-transformers` pip install, encode all `.md` files chunked by section, cosine-similarity search at query time, no server/vector-DB needed at this corpus size (a flat numpy array + argsort suffices).
- **nomic-embed-text-v1.5** — 137M params, ~274MB, 8192-token context (handles a whole long memo/IC-memo in one embedding without chunking), still CPU-viable on a laptop. Better retrieval quality than MiniLM, matters more if memo files get long (IC memos, deep-dive forensics can run long). **WATCH-to-NOW**: use this instead of MiniLM specifically if we find chunking long memos hurts retrieval quality in practice — reasonable upgrade path, not urgent enough to build both.
- **bge-small-en** — 33M params, competitive with MiniLM at similar size, no clear advantage over all-MiniLM-L6-v2 for our use case. SKIP (redundant with MiniLM pick).
- **Fin-E5** (finance-domain embedding, see §1) — best-in-class for finance-specific retrieval per FinMTEB, but 7B params is CPU-infeasible for interactive memo search (multi-second+ latency per query on CPU, plus a large disk/RAM footprint for daily interactive use). SKIP for this use case (mismatched tool: our memos are internal prose/decisions, not the specialized financial-jargon-dense corpus Fin-E5 was tuned to beat general embeddings on).
- No vector-DB needed at current scale — flat cosine similarity over a numpy/pickle cache of embeddings is simpler, zero-dependency, and fully sufficient until the KB is 10,000+ chunks (we are nowhere near that). Avoid over-engineering with Chroma/FAISS/etc. until corpus size actually demands it.
